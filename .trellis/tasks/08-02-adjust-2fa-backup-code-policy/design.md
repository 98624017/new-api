# 技术设计

## 1. 范围与边界

本任务修改备用码生成数量和两套前端的展示容器，不改变认证 API 路径、请求载荷、响应字段、备用码格式、哈希方式或数据库结构。

受影响路径：

- 生成：`common.GenerateBackupCodes`
- 初始化：`POST /api/user/2fa/setup`
- 重新生成：`POST /api/user/2fa/backup_codes`
- 展示：Default 的设置/重新生成弹窗与 Classic 的共用备用码列表
- 二开维护：新增 `012-2fa-twenty-backup-codes`

## 2. 生成合同

- 将 `common.BackupCodeCount` 从 4 调整为 20，继续作为生成数量的唯一来源。
- `GenerateBackupCodes` 返回恰好 20 个 `XXXX-XXXX` 格式的码。
- 生成过程中使用集合排除极低概率的随机碰撞，保证用户实际得到 20 个不同代码。
- 保持 `BackupCodeLength = 8`、当前随机字符集、格式化和 bcrypt 哈希逻辑不变。

## 3. 数据与兼容性

- `TwoFABackupCode` 继续一行存储一个 bcrypt 哈希，`is_used` 表示是否消费。
- 不执行迁移，不批量更新、删除或补写现有用户记录。
- 新部署后：新初始化产生 20 条记录；主动重新生成先按现有事务删除旧记录，再创建 20 条记录。
- 现有用户在重新生成前继续使用原有剩余码，状态接口仍准确返回其实际未使用记录数。
- API 继续使用 `backup_codes: string[]` 和 `backup_codes_remaining: number`，调用方无需版本分支。

## 4. 验证性能与残余风险

- 保持现有 bcrypt 默认成本和逐条比对，接受低频生成/验证操作的计算量增长。
- 不引入可查询指纹、新哈希前缀或兼容读取分支，避免扩大认证存储合同。
- 不修复现有非原子消费窗口；在 customization 文档中记录为本次未改变的残余风险。

## 5. 前端展示

- Default 设置弹窗和重新生成弹窗：代码网格改为移动单列、`sm` 及以上双列；列表设置稳定最大高度和纵向滚动。
- Classic 共用 `BackupCodesDisplay`：保留现有响应式列数，为网格增加相同目的的最大高度和纵向滚动。
- 保留现有代码块、编号和“复制全部”操作；不增加下载、打印或新的可见文案，因此不新增 i18n 键。
- 滚动只发生在代码列表内，标题、警告和复制按钮保持可见。

## 6. 测试与门禁

- 在 `common` 添加确定性合同测试：数量为 20、所有代码格式有效、规范化后互不重复。
- 不用随机循环次数或性能阈值做测试；bcrypt 延迟作为设计取舍记录，不建立不稳定计时断言。
- 运行 Default type-check、Default/Classic 格式与 lint、双前端生产构建和相关 Go 测试。
- 新增 `012` 文档与 patch，并让 `make verify-patches` 在重放树运行备用码生成合同测试。

## 7. 回滚

- 回滚源码和 `012` patch 后，后续新生成恢复为 4 个码。
- 已经生成的 20 条记录仍按现有表结构有效，无需数据回滚；用户下次重新生成时才恢复为 4 个。
