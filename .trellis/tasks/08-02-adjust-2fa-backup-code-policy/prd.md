# 调整两步验证备用码策略

## Goal

提高 NewAPI 两步验证备用码在长期使用和多次紧急恢复场景中的可用性，并在安全性、操作便利性和实现复杂度之间选择合适策略。

## User Value

用户不必因为当前备用码数量较少而频繁重新生成，在无法使用验证器时仍有足够的账户恢复机会。

## Initial Context

- 用户观察到当前每次只生成约 4 个备用码，认为数量不足。
- 候选方案 A：每次生成更多彼此独立的一次性备用码，例如 20 个。
- 候选方案 B：保持较少的备用码，但允许每个码使用 5 次或 10 次。
- 当前阶段只做需求与技术方案规划，不开始实现。

## Confirmed Product Decisions

- 每次初始化或重新生成固定创建 20 个彼此独立的备用码。
- 每个备用码继续只能成功使用一次；不增加 5 次或 10 次重复使用能力。
- 不把数量做成管理员配置项或用户可选项。
- 已启用 2FA 的现有用户继续保留当前备用码；不自动失效或静默补发。用户下次主动重新生成时获得 20 个新码，届时旧码按现有合同全部失效。
- 保持现有 bcrypt 哈希和逐条比对机制；接受生成、重新生成及最坏验证路径相对 4 个码约 5 倍的计算成本，不引入新哈希格式或查找索引。
- Default 和 Classic 前端都使用受限高度的备用码列表：桌面双列、移动单列、列表内部滚动。
- 保留现有“复制全部”能力；本次不增加下载或打印，避免敏感代码落盘及额外交互范围。

## Confirmed Facts

- `common.BackupCodeCount` 当前固定为 4，单码为 8 个大写字母或数字并显示为 `XXXX-XXXX`。
- 上游最新 `upstream/main` 仍保持 4 个一次性备用码，没有可直接同步的新策略。
- 每个备用码单独使用 bcrypt 默认成本哈希，存入 `two_fa_backup_codes`；现有表只有 `is_used` 和 `used_at`，没有可用次数或剩余次数字段。
- 成功验证后当前记录被标记为已使用；状态接口返回未使用记录数，Default 和 Classic 前端都把它展示为“剩余备用码”。
- 备用码可用于登录、禁用 2FA、通用高危操作验证以及查看渠道密钥等安全路径。
- 重新生成会在事务中删除该用户全部旧备用码，再写入新码，因此旧码立即失效。
- 当前校验会读取全部未使用码并逐个执行 bcrypt 比对；把数量从 4 提到 20 会把最坏情况下的单次校验成本放大约 5 倍。
- 两套前端都按数组展示并支持一键复制；Default 使用固定双列、较窄且自动高度的弹窗，20 个码需要限制高度或优化布局，Classic 的双列布局也会明显变长。
- 当前没有针对生成数量、一次性消费、重新生成失效或并发消费的专门回归测试。
- 当前一次性消费是“读取未使用记录后再保存 `is_used=true`”，没有事务行锁或带 `is_used=false` 条件的原子更新；同一码在并发请求下存在重复成功窗口。
- 生成 20 个彼此独立的一次性码仍可沿用现有“一行一码、`is_used` 标记消费”的表结构，以及 `backup_codes: string[]` / `backup_codes_remaining` API 合同；不需要数据库迁移或改变单码语义。

## Preliminary Recommendation

- 保持每个备用码只能使用一次，不引入 5 次或 10 次重复使用。
- 按用户决定采用 20 个一次性码；实现需评估线性 bcrypt 校验成本，并让两套前端在桌面和移动端可完整查看、复制这些代码。

## Requirements

- 保持备用码能够在两步验证不可用时完成账户验证或恢复。
- 明确生成数量、单码消费语义、重新生成行为和旧码失效规则。
- 方案必须考虑备用码泄露后的风险，不得把便利性提升建立在隐式降低账户安全性之上。
- 兼容现有用户已有备用码，不执行数据迁移或强制重新生成。
- 保持“重新生成使全部旧码失效”的现有安全合同。

## Acceptance Criteria

- [x] 已从代码确认当前备用码的生成数量、存储格式、校验与消费路径。
- [x] 已比较“20 个一次性码”与“少量可重复码”的安全性、数据模型、兼容性和用户体验。
- [x] 已确定采用固定 20 个一次性码。
- [x] 已明确后端、前端、测试和迁移范围。
- [x] 已明确保持现有生成与验证机制，并记录不纳入范围的残余风险。
- [x] 新初始化或重新生成 2FA 备用码时，API 返回恰好 20 个格式有效且互不重复的备用码。
- [x] 每个备用码仍只能按现有流程成功使用一次；重新生成后所有旧码失效。
- [x] 升级不会修改现有用户的备用码记录；现有用户主动重新生成后才切换为 20 个新码。
- [x] Default 和 Classic 前端在移动端与桌面端均能完整查看并复制 20 个码，代码列表不会撑出视口。
- [x] 不新增备用码下载、打印、次数配置或数据库字段。
- [x] 生成数量回归测试、双前端检查及完整 customization patch 重放门禁通过。

## Out of Scope

- 在规划获批前修改生产代码或数据库。
- 改变 TOTP、Passkey 或其他认证方式本身的验证规则。
- 修复现有备用码“读取后再标记”的并发重复消费窗口；该边界与本次数量调整无直接依赖，作为已知残余风险单独处理。
