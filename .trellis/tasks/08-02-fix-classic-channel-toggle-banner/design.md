# 技术设计

## 1. 边界

改动限定在 classic 渠道状态调用、classic 全局布局横幅及本地二开登记。后端专用状态接口和 default UI 已符合合同，不修改。

## 2. 渠道状态数据流

1. 渠道表操作列继续把 `id` 与 `enable` / `disable` 动作交给 `useChannelsData.manageChannel`。
2. 状态动作映射为目标值：启用为 1，手动禁用为 2。
3. classic 渠道 API 服务调用 `POST /api/channel/:id/status`，载荷为 `{ status }`。
4. API 返回 `success: true` 后显示成功提示，并通过现有 `refresh()` 按当前分页、搜索、类型和状态筛选重新读取服务端数据。
5. 列表响应使用 `total` 和 `pageSize` 计算有效页码；请求页越界且仍有结果时，重新请求最后有效页，空结果直接回到第 1 页。
6. API 返回业务失败时保留当前列表状态并显示后端消息。

将状态请求放在独立 API 服务函数中，是对稳定后端合同的封装，并提供直接的回归测试边界；不在 UI 测试中依赖整个复杂 Hook 的内部状态数量。

## 3. 状态一致性

- 不直接修改调用方持有的 `record`。
- 不把状态接口返回的布尔 `data` 当作渠道对象读取。
- 成功后复用现有 `refresh()`，让状态筛选、搜索结果和标签聚合由服务端查询结果重新派生。
- 普通列表和搜索列表共用纯分页函数，避免两条请求路径产生不同的越界行为。
- 现有请求计数器继续丢弃过期列表响应；本任务不新增全局并发机制。

## 4. 横幅移除

- 从 `PageLayout` 删除组件 import 与挂载点。
- 保留 `ClassicFrontendDeprecationBanner.jsx`、专属样式和翻译资源，不采用仍会执行组件逻辑的 CSS `display: none`。
- 该方案只停止组件挂载，运行时不再渲染横幅或执行其 `localStorage` 逻辑，同时保持改动最小、易于恢复。

## 5. 测试与二开

- Bun 单元测试验证状态服务对启用和禁用都使用正确 URL、POST 方法和 `{ status }` 载荷，并锁定总数缩减后的有效页码规则。
- classic 生产构建验证停止挂载后仍可编译。
- 新增 `011-classic-channel-status-and-banner` 文档与 patch，并把测试纳入补丁重放门禁。
- `make verify-patches` 从锁定基线重放全部补丁并验证双前端构建和定向测试。

## 6. 回滚

`011` 是补丁链末尾的独立差异。回滚时移除该补丁及登记，并恢复源码对应变更；不需要数据库迁移或配置回滚。
