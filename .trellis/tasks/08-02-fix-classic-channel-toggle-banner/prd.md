# 修复经典 UI 渠道启停并移除维护横幅

## Goal

修复经典 UI 渠道列表中启用/禁用操作失效或只能单向切换的问题，确保操作结果与后端状态一致；同时移除经典 UI 中“旧 UI 停止维护”的警告横幅。

## User Value

管理员能够在经典 UI 中可靠地管理渠道状态，不必切换到其他界面或重复操作；继续使用经典 UI 时不再看到停止维护提示。

## Confirmed Facts

- 问题范围限定在 `web/classic/` 的渠道启用/禁用交互。
- 修复来源优先级为：远端上游最新实现，其次相关 Issue 中已验证的方案，最后基于本仓库调用链自行修复。
- 需要移除经典 UI 的旧 UI 停止维护警告横幅。
- 不修改受保护的项目或组织标识。
- 后端 `PUT /api/channel/` 明确拒绝包含 `status` 的请求；渠道状态必须通过 `POST /api/channel/:id/status` 更新。
- classic 的 `useChannelsData.manageChannel` 仍通过旧 `PUT` 接口发送 `{ id, status }`，因此启用和禁用都会稳定返回“无效的参数”。
- 上游 Issue #5891 与 #5918 记录了同一复现路径；PR #5919 给出了专用状态接口修复，但因上游决定移除 classic 而未合并，并非方案存在技术问题。
- 当前上游 `main` 已整体删除 `web/classic/`，因此无法从最新版正式代码直接同步 classic 修复。
- 横幅由独立组件、`PageLayout` 挂载点、专属 CSS 和三组专属翻译键组成；其他“关闭提示”等通用翻译仍有调用方，不能一并删除。
- 本仓库要求运行时行为差异作为编号二开维护，因此本任务需要新增 `011` customization 文档与 patch。

## Requirements

- 查明渠道启停操作的真实失败模式和根因，覆盖启用与禁用两个方向。
- 若上游已有兼容当前代码的修复，按其最新实现同步；否则评估 Issue 方案，再实施最小范围修复。
- 成功操作后，经典 UI 列表展示的渠道状态必须与服务端持久化状态一致。
- 状态筛选或搜索结果因切换状态而缩减时，当前页不得停留在超过新总数的空白页。
- 失败操作必须保留原状态，并继续向用户显示可理解的错误反馈。
- 停止在经典 UI 中挂载旧 UI 停止维护警告横幅，不影响其他通知或页面布局。
- 采用最小改动，只删除 `PageLayout` 的组件 import 与渲染节点；保留横幅组件、样式和翻译，方便恢复并降低补丁冲突风险。
- 保持后端 API 合同以及 default UI 行为不变，除非定位结果证明共享层存在必须修复的问题。

## Acceptance Criteria

- [x] 在经典 UI 渠道列表中，可将已启用渠道禁用，服务端状态与列表状态同步更新。
- [x] 在经典 UI 渠道列表中，可将已禁用渠道重新启用，服务端状态与列表状态同步更新。
- [x] 启停请求使用 `POST /api/channel/:id/status`，请求体只包含目标 `status`；不再向通用更新接口发送状态字段。
- [x] 成功后重新加载当前查询条件下的渠道数据，状态筛选、搜索结果和标签聚合不会保留陈旧展示。
- [x] 当前页因结果总数缩减而越界时，普通列表和搜索列表均回退到最后有效页；空结果回到第 1 页。
- [x] API 失败时不会显示虚假的成功状态，并保留现有错误提示能力。
- [x] 经典 UI 不再渲染旧 UI 停止维护警告横幅。
- [x] 自动化测试锁定 classic 状态更新的 URL、HTTP 方法和请求体；经典 UI 构建通过。
- [x] 新增并登记 `011` customization 文档与 patch，`make verify-patches` 通过。

## Out of Scope

- 重新设计经典 UI 的渠道页面。
- 修改 default UI 的渠道管理交互。
- 删除经典 UI 中与停止维护警告无关的其他通知。
- 清理未挂载横幅的组件、样式和翻译资源。
