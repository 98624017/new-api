# new-api 生产备份分析

默认数据源是生产备份服务在 R2 发布的最新成功快照。先核验来源与完整性，再分析业务事件；把已证实的事实、可能原因和证据缺口分别说清楚。

## 1. 确定问题和项目

- 读取目标 `new-api` 仓库的 `AGENTS.md`，核对 `model/token.go`、`model/log.go` 等入口。当前目录不是该仓库时，定位正确仓库后再解释业务行为。
- 从请求提取目标（key、用户、兑换码、任务、渠道或模型）、现象、时间范围和筛选条件。未给时间范围时先查目标全部保留记录；给了月份但未给年份时结合当前日期和备份时间确定并注明。
- 时间默认使用用户当前时区；无可用时区时采用 `Asia/Shanghai` 并明示。把日/月区间转换为 UTC 的 `[开始, 下一日/月开始)`，保留“创建时间”与“兑换/消费时间”的区别。
- “大于 1000”采用严格 `>`。金额阈值先确定币种和 quota 换算依据，名称只作为标签。

完成条件：明确分析对象、时间与单位，已经确认业务代码所在仓库。能从现有配置查证的内容直接查证。

## 2. 获取最新成功备份

完整读取 [R2 备份获取流程](references/r2-backups.md)，按其中步骤获取并校验备份。

- 每次新排查刷新 `full/latest.json`，用 manifest 固定本次快照。下载期间指针更新时，继续使用已固定的对象并记录抓取时间。
- 用户明确指定历史对象或已有本地备份时使用指定来源，并标注历史快照；已有文件不自动替代本次最新备份。
- 记录 bucket、完整 object key、`created_at`、文件大小、SHA-256、完整性结果及快照距当前时间的差值。按 manifest 的 `excluded_fields` 标明证据范围，旧快照缺少该声明时记为“未声明”。

完成条件：已拿到对应实例的完整备份，大小、SHA-256 和压缩完整性均通过；或已明确说明缺少的访问配置/备份格式支持，不能把失败的下载当成数据源。

## 3. 建立可复核的数据读取

先完整读取 [数据分析约定](references/data-analysis.md)，再执行查询。

- 从备份实际的建表声明、`COPY` 表头或数据库 schema 映射列名，读取版本信息和可用表；按本次问题选择关联表。
- 默认流式解析压缩 SQL，合并同一轮独立统计，避免每条问题都完整扫描大文件。
- 保存必要的查询条件、关联规则和聚合结果；原始密钥、兑换码和无关用户行留在受保护的原始备份中。
- 需要复杂联查时可提出隔离副本方案；数据库恢复或结构/数据操作遵循当前用户和项目授权，确认目标为本地一次性实例后执行。分析事务使用只读模式。

完成条件：字段按实际 schema 解释，解析无静默跳行，能说明时间覆盖、关联依据及缺失记录。

## 4. 沿业务链验证原因

按问题选用以下分支；每个分支同时检查数据和对应代码。

| 问题 | 核查顺序 |
| --- | --- |
| key 额度变化 | 精确定位令牌 ID/所属用户 → 当前剩余及已用额度 → 消费与退款 → 指向令牌的兑换/充值 → 管理审计 → 资金与令牌更新路径 |
| 兑换码/充值去向 | 创建者与兑换者、事件时间、状态 → 按兑换码/订单 ID 核实入账金额与去向 → 对照当前面额、创建审计与额度更新 |
| 消费突增 | 每时段次数与扣费、模型与渠道 → 请求 ID、错误与任务结算关联 → IP/代理来源 → 计价和参数校验 |
| 任务失败/退款 | task ID 与令牌 → 预扣、终态、差额结算/退款 → 钱包/订阅资金来源 → 是否恢复令牌额度、是否有重复结算 |
| 模型/渠道故障 | 错误时间分布、渠道/模型 → 关联请求和任务 → 备份里的配置 → 适配器、路由和错误处理 |

- 管理审计的日志归属用户可能是操作者；用 `other.op.params` 等字段识别目标资源。先确认生产版本的审计语义。
- 金额异常沿输入/配置 → 计价 → quota 转换 → 预扣 → 结算/退款追踪；动态计价额外读取 `pkg/billingexpr/expr.md`。
- 同时核查相反证据：例如退款是否确实属于目标令牌、同一兑换码是否出现多笔入账、名称与金额是否仅是标签差异。
- 只有消费/错误记录时继续查没有 `token_id` 的充值和管理日志，不能据此断言没有加额。日志不完整时用兑换码/订单/任务记录交叉核验。
- 记录仓库 commit 和可确认的生产版本。版本不一致或无法确认时，当前代码只用于解释候选机制，不能代替事发时的证据。

完成条件：每项结论都有记录 ID、时间、关联字段或代码依据；未覆盖的层明确作为未知，不把累计字段与保留流水的差额直接判成异常。

## 5. 交付与收尾

默认用简体中文，先给结论，再给最小充分证据：

1. 快照来源、截止时间、查询时区和范围。
2. 事件数量、金额合计和目标；多笔事件用表格展示日期、记录 ID、名称、实际额度及去向。
3. 可确认的触发事件、原因及影响；推测附上证据缺口和下一项验证。
4. 数据或日志覆盖限制，必要时给出可复现的筛选与聚合条件。

密钥默认只展示尾部少量字符或令牌 ID，不输出完整 key、兑换码内容、密码、访问凭证、完整 `other` 或请求载荷。IP 仅在来源分析需要时展示。

本 Skill 授权范围为读取 R2 备份和本地分析。生产调额、撤销兑换、变更配置、重试真实请求、部署和修改 R2 对象均需相应的明确授权，分析请求本身不包含这些操作。

完成后删除本次不再需要的下载和临时分析文件；需要继续排查时保留受保护的临时目录并给出路径和快照身份。可复用的查询应脱敏，原始备份及凭证不进入仓库。

## 调用示例

- `$newapi-production-analysis 查这把 key 最近一次额度增加的来源。`
- `$newapi-production-analysis 查 2026 年 9 月金额 > 1000 USD 且兑换到 key 的兑换码，列名称、实际额度、兑换时间和去向。`
- `$newapi-production-analysis 分析昨晚视频任务失败率和退款，确认有没有重复退款。`
