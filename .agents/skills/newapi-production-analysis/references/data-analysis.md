# 备份数据读取和事件解释

## 读取 SQL gzip

先从解压流的头部确认数据库格式、服务端版本、`pg_dump` 版本和 schema。压缩文件必须经过 gzip 读取，不直接对 `.gz` 运行文本 `sed`/`rg`。大型备份优先单进程流式扫描，避免并发重复解压竞争资源。

PostgreSQL plain SQL 的读取约定：

- 按 `COPY schema.table (columns...) FROM stdin;` 的列名建立映射，每张表读取到独立的 `\.` 结束行；支持带引号的列名和实际 schema。
- 数据先按实际 tab 分隔，再按 PostgreSQL COPY text 规则单次解码转义；字段为原始 `\N` 时才解释为 NULL。正确区分 `\\`、`\t`、`\n`、`\r`、其他 COPY 转义和转义后的字面量 `\N`。
- `other`、设置和任务 JSON 在 COPY 解码后再做 JSON 解析。不要串联字符串替换，以免二次解释原本的字面反斜杠。
- 明确区分 NULL、空字符串、整数零和布尔值。金额/quota 聚合使用整数或 Decimal，不经过浮点累加。
- 行列数、UTF-8、数字或 JSON 不合法时报告表、行号和字段名，保持敏感原文不输出；不能用 `errors="replace"`、`except: continue` 或返回空对象掩盖解析失败。
- 遇到 COPY CSV、二进制、自定义 dump 或非 PostgreSQL 备份时使用对应数据库工具/解析规则，不能套用上述 tab 格式。

解析脚本是分析工具，不执行备份中的 SQL 或嵌入命令。复杂查询确需恢复时使用明确授权的隔离实例；绝不将 dump 的 `DROP`/`CREATE` 语句指向生产。不要启动 new-api 连接副本，因为启动可能执行 AutoMigrate、轮询任务或调用真实上游。

## 目标关联

用实际 schema 确认下列语义，并与本次代码版本交叉核验：

| 数据 | 主要关联 |
| --- | --- |
| `tokens` | `id`、`user_id`、key 的完整精确匹配、name、remain/used quota、unlimited 标志 |
| `logs` | user/token ID、type、created_at、quota、request/task ID、channel/model、`other` 中的结构化审计 |
| `redemptions` | ID、快照时的 quota、status、created/redeemed_time、创建者 user_id、used_user_id |
| 充值/订阅订单 | 订单/交易 ID、支付状态、金额、资金来源与回调/入账日志 |
| 异步任务 | task ID、user ID、私有计费上下文里的 token ID、预扣额度、终态和结算 |

按来源入口还原令牌主体，再与 `tokens.key` 做完整精确匹配。当前 relay 的 `TokenAuth` 去掉 Bearer 包装和可选的 `sk-` 后，以第一个 `-` 前的主体查库。管理员可在主体后附 `-<渠道ID>` 指定渠道。自助接口的 `TokenAuthReadOnly` 同样按主体查库，只读认证规则见 `middleware/auth.go`。已有数据库 key 用其存储原值匹配。查到行只确认令牌身份，请求是否成功还需核对入口权限与事发记录。报告只展示令牌 ID 或必要的脱敏标识。

充值日志可能只有 content，没有 `token_id` 或 `quota`。优先按兑换码/订单 ID 关联记录，结构化审计优先于自然语言。在当前自助兑换实现里，日志会写入兑换码 ID 和“兑换到令牌「名称」”；名称可能重名或事后改名，只能证明记录当时的目标标签，不能据此强行关联唯一 key ID。

批量兑换查询同时保留“已确认到令牌”“已确认到钱包”“去向未覆盖”三类计数，避免未匹配日志的记录被过滤后静默消失。按兑换码 ID 去重计数，另行检查多条入账日志；同名令牌合并金额只作为名称汇总，不称为确定的唯一 key 数量。

## 额度与日志类型

日志类型以对应生产版本 `model/log.go` 为准。当前定义可作为读取入口：

| type | 语义 | 分析注意点 |
| ---: | --- | --- |
| 1 | 充值 | quota 字段可能为 0，金额/去向在内容或订单/兑换码中 |
| 2 | 消费 | 正 quota 通常表示扣费量，不是余额增加；差额补扣也可能在此 |
| 3 | 管理 | 审计归属操作者，目标在 op.params 等字段 |
| 4 | 系统 | 可能是赠额，也可能只是验证/安全事件，逐条核实 |
| 5 | 错误 | 不能单独判断是否发生预扣、退款或最终上游结果 |
| 6 | 退款 | 核验 task/token、退还资金来源、恢复令牌开关和重复结算 |
| 7 | 登录 | 用于必要的身份/来源交叉核验 |

账户钱包和令牌限额分别更新，并不代表两次货币入账。核查 `model/redemption.go`、`model/token.go`、`model/user.go` 与 `service/task_billing.go` 中的实际资金路径。

兑换码名称是自由标签。`redemptions.quota` 即使在兑换后也可修改，历史入账金额优先按带该兑换码 ID 的充值流水核实，保留日志的显示单位与精度。当前 `redemption.create` 审计只记录整批名称、数量和格式化面额，未列出每个兑换码 ID。同名批次缺少唯一关联时，将该码的创建面额及变更原因标为未知。确认应发面额后，再判断误发或计算差额。

quota 转换读取 `common.QuotaPerUnit`、`logger.LogQuota` 和币种展示设置；当前日志显示的币种还受配置影响。按单位过滤并同时保留原始 quota。历史配置未知时注明换算依据，不能从名称猜金额或把所有货币符号当 USD。

## 证据强度与覆盖

- 明确列出查询区间实际覆盖的最早/最晚记录，以及是否配置独立日志库、ClickHouse、关闭消费日志或有清理策略。主库 dump 可能不含生产日志库。
- 当前 `used_quota` 是累计字段，保留消费日志只是可见区间；差额也可能涉及其他计费路径或调整。`remain_quota + used_quota` 本身不证明初始授额或完整入账历史。
- request ID 唯一只证明日志关联标识不同，不能证明调用来自不同人、上游一定成功或没有重复业务任务。真正结果需结合状态、错误和结算事件。
- IP 可能来自代理、云出口或转发头。结合可信代理配置分析来源，不能因多 IP 就认定泄露/滥用。
- 快照证实的是备份时保存的状态；单个快照不能恢复未留审计的全部历史余额，也不能回答快照之后的事件。

报告至少核对明细笔数、按记录 ID 去重笔数、总 quota 与分组汇总是否一致。指出疑似异常时说明相反证据和未确认事项。
